# Hermes + Gemma4 算法设计

处理超大日志文件（例如几个 GB 甚至更大的 logcat 导出文件）时，核心挑战在于**内存管理**。如果使用 `read().splitlines()`，程序会尝试将整个文件加载到 RAM 中，内存占用太大。

为了实现低内存占用且高效的过滤，我建议采用：

> **“正向定位锚点 + 倒序块扫描”的算法设计**

------

# 详细设计方案

## 1. 核心算法思路：双阶段扫描法（Two-Pass Scanning）

不要试图从头读到尾。既然目标是 **am_anr 发生前的 12 秒**，我们应该把 `am_anr` 视为时间锚点（Anchor）。

------

### 第一阶段：正向流式搜索（Forward Streaming Search）

* 操作：使用流式读取（逐行读取，不加载全文）从文件头开始扫描

* 目的：查找第一个出现的 `am_anr` 字符串

* 关键点：一旦找到 `am_anr`，立即记录两个核心数据：
  1. **时间戳（Timestamp）**：该行的发生时间
  2. **字节偏移量（File Offset）**：使用 `file.tell()` 获取当前行在文件中的物理位置

* 内存占用：极低，仅保留当前读取的一行

------

### 第二阶段：倒序块扫描（Reverse Chunked Scanning）

这是算法的关键优化点。一旦有了 `am_anr` 的 offset，不需要回到文件开头，而是从该位置**向前回溯**。

* 操作步骤：
  1. 使用 file.seek(offset) 将文件指针移动到 `am_anr` 所在位置
  2. 以固定大小的块（Chunk，例如 64KB）为单位，向文件头方向进行**倒序读取**
  3. 逻辑判断：
     1. 在每个块中：解析每一行的时间戳
     2. 终止条件：如果某一行时间戳 < `(am_anr_timestamp - 12s)`立即停止扫描（因为更早的日志不符合要求）
     3. 过滤逻辑：时间在 12s 窗口内，且符合“Tag 匹配” 和“包名匹配”规则，则将该行放入结果列表。

- 内存占用：仅取决于 **12 秒内符合条件的日志量**（通常非常小），而不是整个日志文件大小。

------

## 2. 算法架构图

```
[ 巨大的 Log 文件 ]

| [ 不相关日志 ... ] —— (阶段1：逐行扫描，极快)
| 
| [ am_anr 出现! ] ← 记录 Timestamp 和 Byte Offset
|
| [ 12s 窗口开始 ] ← (阶段2：从 offset 开始向前倒序读取 chunk)
|   [ 相关的 Tag 日志 ]
|   [ 相关的 Tag 日志 ]
|
| ---- 时间边界 (T - 12s) ----
|   [ 甚至更早的日志 ... ] → （停止扫描，释放资源）
```

------

## 关键总结（工程视角）

这个方案本质是：

| 维度       | 方案                           |
| ---------- | ------------------------------ |
| IO 模型    | 顺序读 + 局部逆序读            |
| 时间复杂度 | O(N) + O(K)（K为窗口大小）     |
| 空间复杂度 | O(1) ~ O(K)                    |
| 优势       | 避免全量加载，适用于 GB 级日志 |

------

## 额外工程优化建议（基于经验）

1. **chunk 边界处理**
   - 需要处理跨 chunk 的半行（buffer 拼接）
2. **时间解析优化**
   - 避免 regex，使用定长 slice 提速
3. **mmap 替代（可选）**
   - 对极大文件可进一步优化 IO
4. **并行优化（谨慎）**
   - 倒序扫描阶段可做分块并行，但需保证时间顺序
